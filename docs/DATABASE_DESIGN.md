# ParkVanta — Database Design

PostgreSQL 16 · SQLAlchemy 2.1 · Alembic. UUID primary keys, UTC timestamps, foreign keys on every relationship.

## 1. Entity groups

```text
Organizations → Properties → Towers → Apartments → Residents (users + resident_profiles)
Properties → Parking Zones → Parking Slots → Reservations → Occupancies
Invitations → QR Passes → Entry/Exit Events
Audit Logs · Notifications · Society Policies · Refresh Tokens · Password Reset Tokens
```

22 tables are created by the initial migration (`139d935f5774`). The current head adds the offline ledger,
notification outbox, durable event archive, worker heartbeats and hot-path indexes: **25 tables across 6 migrations**.

## 2. Key tables

| Table | Purpose | Notable constraints |
| :--- | :--- | :--- |
| `organizations` | Society/tenant root | `slug` unique |
| `properties` | Physical community | `organization_id` FK, timezone |
| `apartments` | Unit inventory | unique `(property_id, number)` |
| `users` | All identities | `email` unique, role string, suspension flags |
| `resident_profiles` | Unit binding + verification | `user_id` unique |
| `guard_profiles` | Property assignment | `user_id` unique |
| `visitors` | Visitor identity per property | index `(organization_id, phone)` |
| `vehicles` | Normalised registration | unique `(organization_id, registration_number)` |
| `invitations` | Visit request and approval | index `(property_id, status)` |
| `qr_passes` | Hashed single-use token | `token_hash` unique, `invitation_id` unique |
| `parking_zones` | Physical parking area | unique `(property_id, name)` |
| `parking_slots` | Individual bay | unique `(property_id, code)` |
| `parking_reservations` | Slot held for a visit | **partial unique active slot** |
| `parking_occupancies` | Vehicle physically inside | **partial unique active slot**, unique reservation/invitation |
| `entry_exit_events` | Immutable gate decision trail | index `(property_id, created_at)` |
| `audit_logs` | Security-critical actions | JSON metadata |
| `society_policies` | Per-property rules | `property_id` unique |
| `refresh_tokens` | Rotating sessions | `token_hash` unique |
| `worker_heartbeats` | Last successful expiry/notification run | `worker` primary key |

## 3. Critical invariants and how they are enforced

| Invariant | Enforcement |
| :--- | :--- |
| One active occupancy per slot | Partial unique index `uq_active_occupancy_slot` |
| One active reservation per slot | Partial unique index `uq_active_reservation_slot` |
| One reservation and one occupancy per invitation | `UNIQUE` on `invitation_id` |
| One active pass per invitation | `UNIQUE` on `qr_passes.invitation_id` |
| Pass is single-use | Conditional `UPDATE … WHERE status = 'ACTIVE'` |
| Slot compatibility | Allocation query filters `vehicle_category IN (class, 'ANY')` |
| Tenant scoping | `organization_id` / `property_id` on scoped tables, service assertions |
| Timezone correctness | `timestamptz` everywhere; display conversion in the client |

Partial index (PostgreSQL):

```sql
CREATE UNIQUE INDEX uq_active_reservation_slot
  ON parking_reservations (slot_id) WHERE status = 'ACTIVE';
```

## 4. Allocation query

```sql
SELECT s.*, z.priority
FROM parking_slots s
JOIN parking_zones z ON z.id = s.zone_id
WHERE s.property_id = :property
  AND s.status = 'AVAILABLE'
  AND z.is_active
  AND z.category = ANY(:categories)
  AND s.vehicle_category IN (:vehicle_class, 'ANY')
ORDER BY z.priority, z.name, s.code
LIMIT 1
FOR UPDATE OF s SKIP LOCKED;
```

`SKIP LOCKED` gives each concurrent transaction a different candidate; the unique index is the final backstop.

## 5. Lifecycle and cleanup

- Reservation TTL: `reserved_until` set from the invitation's expected departure.
- Worker `app.workers.expiry` expires passes, reservations and stale pending invitations, and flags overstays.
- Workers upsert `worker_heartbeats` in the same transaction as their results; `/metrics` and
  `app.workers.health` read it to detect a stopped scheduler.
- Every sweep is idempotent: transitions are conditional on current state.

## 6. Retention

| Data | Retention (proposed) |
| :--- | :--- |
| Visitor contact and vehicle | 90 days after visit, configurable |
| QR pass hashes | 90 days, then purged |
| Entry/exit events and audit logs | 24 months (security requirement) |
| Camera images (future vision) | Not retained unless explicitly enabled |

## 7. Migrations

```bash
cd backend
alembic upgrade head
alembic revision --autogenerate -m "describe change"
```

Autogenerated migrations are reviewed before commit. Production schema changes never happen by hand.
